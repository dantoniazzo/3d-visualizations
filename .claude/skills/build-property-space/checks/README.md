# Static checks for a built space

Read-only Node scripts that audit a seeded scene (or the generator's output) without opening the app:
furniture layout and walkability, stairs and routes, every hinged door's hand and swing, the street
entrance flights, z-fighting, building C's grade, and the people planner's rules over many seeds.
They were written for Ladonia
(`scenes/kosinozici-villas.json`, generated by `scripts/spaces/ladonia/*.js`) and are kept here as
working templates for the next project.

**On a new space, as shipped, most of them still audit Ladonia** — they say nothing about yours and
can look like a pass. `furniture-check.mjs`, `furniture-check-c.mjs` and `c-grade.mjs` always read
`scenes/kosinozici-villas.json` and the `ladonia` generator. `zfight-check.mjs scenes/<id>.json` and
`stairs-check.mjs --scene scenes/<id>.json --no-sim` work on any scene for their per-surface and
per-flight rules (stairs-check's named routes are Ladonia's and are skipped). `doors-dump.mjs` and
`door-swing.mjs` are project-agnostic: give them `--scene scenes/<id>.json --gen
scripts/spaces/<project>` (only their defaults are Ladonia's). `people-plans.mjs <scene-id>` is
project-agnostic too, and has no default scene. `entrance-check.mjs` exits 1 with
"nothing checked" unless the street flights' ids start `steps-`. For a new project, copy a checker
to `checks/<project>-<name>.mjs` (same folder, so the repo is still found four levels up), change
what each section below lists as Ladonia-specific, and make sure it reports your building ids before
trusting a pass.

They run in node, from the spec and the app's own builders: nothing a tab draws reaches them. So the
editor's plain light and view scope (since 2026-10-10 an editor tab opens with the houses alone
drawn, the garden not even made), and its stand-ins and frames on demand (since 2026-10-13 the
house and the furniture are drawn by merged and instanced copies, and a tab at rest draws nothing),
change nothing here; it is the in-page helpers that read what is drawn, and `zfight.js` and
`people-audit.js` ask for the whole site themselves, `zfight.js` passing over the stand-ins
(SKILL.md's list of files, and its §10 for a helper of your own). All nine checkers were run against
the app as it stood on 2026-10-12, after the performance work: every one still ran, with Ladonia's
results as the sections below record them (stairs-check 0 blockers, 5 majors, 3 minors; door-swing
71 leaves, no contact over 5 mm on the mesh; every street flight passing; people-plans no problems
over its seeds). One of them imports code the editor's work of 2026-10-13 rewrote —
`stairs-check.mjs` builds its trees with `Collision.js`'s `buildOctree` — and was run again on
2026-10-14: the same 0 blockers, 5 majors and 3 minors, every flight and route OK. The others import
only the validator, the catalogue, `Door.js` and the landscape, none of which that work touched.

Run them from the repo root, e.g. `node .claude/skills/build-property-space/checks/stairs-check.mjs`.
Each finds the repo four directories above itself (checks -> build-property-space -> skills ->
.claude -> repo); set `REPO=/path/to/checkout` to point one at another checkout. They import the
app's own modules (`server/scene/validate.js`, `shared/landscape.js`, `shared/catalog.js`,
`frontend/Experience/...`, `node_modules/three`), so `npm install` must have run. Nothing writes to
the repo; output goes to stdout unless a flag names a file or directory.

Seeded vs live: by default each reads `scenes/kosinozici-villas.json`. If you have edited the
generator but not re-seeded (`node scripts/seed-scenes.js kosinozici-villas`), use the script's live
flag (`--live`, `--gen`, `--source`, or `--code --validate` for c-grade), which runs the generator
through `validateScene` as seeding does; entrance-check has none (re-seed, or pass a scene file).
`furniture-check.mjs` and `c-grade.mjs` say when the seeded scene differs from the generator — which
also happens when the user has edited the scene in their editor: diff before re-seeding, and carry
their edits into the generator. furniture-check compares the scene with the generator's output run
through `validateScene`, as seeding writes it, so the validator's sub-millimetre clamping of
openings to their walls is not reported as a difference; c-grade checks C's ids, and its furniture's
catalogue ids and plan positions to 1 mm, against `c.js` and `furnish.js` run directly. A generator
*copy* (`--gen=`, `--gen-dir`, `--src`, `--code=`, or `--live --gen <dir>` for the door tools) must
sit three levels below a `public` that is, or links to, the repo's `public` (`furnish.js` reads
`../../../public/models/furniture/catalog.json`), e.g. `<scratch>/gen/scripts/spaces/ladonia` with
`<scratch>/gen/public -> <repo>/public`.

## furniture-check.mjs: furniture, doors, stairs and reach in A/B

Per building, floor and room, it checks furniture-on-furniture overlaps (and rug/coplanar-top
z-fighting), furniture in walls or openings and in the landscape's solids (pergola posts, hedges,
planters, pools, rails), stacked pieces standing on something of the right height, pendants hung
lower than the walker over open floor, a door-wide 0.9 m clear zone each side of every door, clear
stair footprints with 1.0 m landings, reach (a 0.05 m raster flood of the player's 0.35 m capsule
from the building's `entrance` spawns up through the stairs, so every door, stair end and furniture
access side must be reachable, and passages under 0.75 m are reported with their pinch point),
spacing rules (bed sides, chairs, sofa to coffee table, kitchen, WC, shower, wardrobe fronts), tall
pieces in front of windows, and pieces in the wrong room. Each finding gives the piece's index, id,
catalog id, site and building-local position, and the `furnish.js` line that placed it. Run `node
.../furniture-check.mjs [AB|A|B]` (default AB). Its `C` mode is broken (it counts C's −1.0 ground
rooms as many floors and reports false "no way onto this floor"): use `furniture-check-c.mjs` for C.
Flags: `--live` (generator output, no re-seed), `--gen=<dir>` (a copy of the generator, used for
source lines and the staleness note; add `--live` to check its output), `--floor=<elev>` (computes
only the ground floor and that one, so a floor above the first gets false reach blockers, and it
prints the ground floor's findings too), `--json`, `--maps` (ASCII reach maps at 0.1 m per
character, printed after the report, to stderr under `--json`), `--maps=<dir>` (writes
`map-<b>-<floor>.txt` there instead), `--probe=x,z,floor` (building-local reach and pinch at a
point). Look for the `NOTE: the seeded scene differs` line and the closing `SUMMARY: N findings,
blocker/major/minor; by check {...}`. Blockers come first in each floor. Ladonia-specific: `OFFSETS`
(A [0,0], B [0,24.2], C [2.5,-21]), the generator file names (`kit.js`, `index.js`, `furnish.js`,
`ab.js`, `c.js`, `Building.put/wall` hooks, the `spaces/ladonia/` stack-frame regex), the scene
path, and its knowledge of the `ld-` pieces, which has to grow with the catalogue:

- `KIND`, catalogue id -> kind, which picks the spacing rule (`ld-dining-oak-4s` and
  `ld-table-round-90` are tables; an id it doesn't know is `other`, with no spacing rule of its own);
- `ROUND`, circular footprints: the round tables (`ld-table-round`, `-90`, `ld-out-table`), the round
  coffee and side tables (`ld-coffee-round-60`, `ld-out-coffee-round`, `ld-out-side`), stumps, round
  rugs and the felt, woven and pleated pendants;
- `localShapes`, footprints that are not the catalogue box: the doubles' 1.84 m base (the duvet's
  overhang is in the catalogue width), the corner sofas' L (`ld-sofa-(boucle-)corner(-s)-l`: the run
  along the back and the return at its own left, each a seat deep, 0.96 or 0.90) and the chaise
  sofas', the L corner kitchens' two 0.62 m legs (`ld-kitchen-<scheme>-l`), the U kitchen's three
  legs as its GLB draws them (`-u`), and the parasol's pole — a piece whose box would wall off the
  floor inside its L or U otherwise reads as a blocker;
- `TALL_MIDDLE`, pieces whose box height is set by a slim part at their middle (the window walk-in
  showers' rain head on its drop rod): under a flight they are measured by their body, 2.11 m;
- the spacing rules for the L kitchen's two fronts and the corner sofa's seat, and the window check
  skipping walk-in showers and the U kitchen (its legs under the windows are base height).

## furniture-check-c.mjs: building C in its own frame

It runs a deeper version of the furniture audit for C. Furniture is measured from the real GLB
triangles rasterised at 2 cm (so an L-sofa or a floating nightstand is judged as drawn), and the
walk raster collides each piece as the game does since 2026-10-16 (`SceneBuilder.collisionOf`): as
the catalogue's `collision` says when that is `box` or `mesh` (the L-shaped sofas are `mesh`), else
as its box when the piece without its opening parts (every node under one with `extras.opens`) has
more triangles than `MESH_COLLISION_BUDGET`, else as its mesh — its parts in their shut places,
which is where the game's shut boxes stand (`_modes.mjs` prints each piece's mode). Until
2026-10-17 the script still boxed every piece with a part that opens, walling off an L or U
kitchen's floor and every wardrobe, nightstand and washer the walker passes: against that copy,
Ladonia's C read ACCESS 12, NARROW 27; with the rule mended, ACCESS 13, NARROW 26. The new ACCESS
is the walk-in shower `c-f071`, whose way in is a glass door: shut in the raster it bars its own
front, as it does in the game until opened (a way in has no shut box: it bars the way itself) —
read an ACCESS on a shower with a door as a note. It checks room membership, overlaps, furniture into walls,
rails, planters, stairs and floor openings, door clearance, swing and reach on both sides, stair
foot and head space, access, narrow passages and cut-off areas, spacing, ordering (TV facing the
sofa), windows and daylight, holes in walls and floor gaps. Each line carries its `furnishC:<line>`
origin. Run `node .../furniture-check-c.mjs`. Flags: `--live`, `--src <dir>` (a generator copy,
implies `--live`), `--budget <n>` (as if `SceneBuilder.MESH_COLLISION_BUDGET` were n; the default is
the app's 12000, which the rebuilt beds, 14,000 to 24,000 triangles, already exceed: they collide
as their catalogue boxes, duvet overhang included), `--map` (ASCII level maps), `--all` (per-room
inventory), `--probe L,x0,z0,x1,z1` (raster cells along a segment on level L — a level index 0/1/2,
not an elevation). Look for the `=== Summary ===` line of CODE counts (DOOR-CLEAR, NARROW, CUT-OFF,
SPACE-*, DAYLIGHT-NONE, FLOOR-GAP and so on); the numbered sections above it give the detail.
Ladonia-specific: `TAG "c-"`, `OFF [2.5,-21]`, the level-defining room ids (`c-g-c1-living`,
`c-f-c4-living`, `c-r-c4`), `LEVEL_NAME`, the `SOUTHWARD` catalog set, the `furnish.js` helper names
and a hard-coded `mirrored` line range (103 to 118) used to label origins (the scan of `function`
lines finds `mirrored()` wherever it is, so the range only matters while line 103 mentions it).

## stairs-check.mjs: every flight and the named routes

It builds the scene's collision as the app does (StructureBuilder slabs, walls, roofs, stair ramps
and rails; LandscapeBuilder terrain and garden pieces; every furniture GLB as `SceneBuilder.collisionOf`
has it since 2026-10-16: the catalogue's `collision` (`none`: left out), else a box only when its
triangles without its opening parts pass `SceneBuilder.MESH_COLLISION_BUDGET` (read from the app),
else its mesh with its parts shut; doors open) with the app's own `Collision`/Octree. Run again on
2026-10-17 with that rule: 0 blockers, 5 majors, 3 minors, every flight's walk and every named route
OK, as before. It hands StructureBuilder a stub
MaterialLibrary (`materials`, near the top): if it crashes with "… is not a function" after an app
change, add that method to the stub, returning `plainMaterial`. Then for each flight it checks rise,
going, width and pitch, headroom along the flight against what the capsule needs, what the capsule
touches standing on the ramp every 5 cm, landing depth at the head and approach at the foot (in line
and to each side), and a simulated walk using Player.js's movement maths. Finally it walks the named
routes (street to garden steps to outside stair to each flat's door, own stair to the roof terrace).
Run `node .../stairs-check.mjs`. Flags: `--gen` (the generator, validated), `--gen-dir <dir>` (a
patched copy), `--scene <path>`, `--no-sim` (rules, headroom and clearance only), `--only id1,id2`,
`--json` (the issue list as JSON after the summary). Look for `WALK: OK` or `FAILED` per flight,
`OK` or `FAILED` per route under `=== named routes`, and `=== summary: N blocker(s), N major, N
minor`. It exits 1 when there is a blocker. Where a flight's head has less than 1 m of landing in
line, its walk steps off sideways (as a person would); the shortfall is still reported as a major.
Ladonia-specific: `FRAMES` (derived from the rooms `a-f-landing`, `b-f-landing` and `c-g-rec-e` at
fixed local corners, falling back to the A/B/C offsets), the `[abc]-` id convention, and every
`ROUTES` entry (stair ids such as `a-stair-out`, `c-stair-out`, door ids, building-local waypoints).
Rewrite the routes for a new project. A route's waypoints are test targets, not constraints on the
plan: put them on floor the plan leaves free, and move a waypoint rather than furniture the plan
draws (A/B's north-roof route ends at local [5.2, 4.4], outside the slider, since the plan's
loungers stand over its old end at [5.2, 3.7]). Ladonia on 2026-10-04: 0 blockers, 5 majors (C's
compact stairs' landings and approaches, known), 3 minors, every flight and route OK.

## doors-dump.mjs: every hinged door's hand, as the app hangs it

It lists every door that swings (`DOOR_TYPES` `hinged` and `double`; sliding and pocket doors are
left out). Each is built with the app's own `Door.js`, in its wall's frame set up as
`StructureBuilder.buildWall` sets it (X along start -> end, side A = +Z, the left of start -> end in
plan), posed through `Door.update` and read back, so the hand, the pivot and the opening angle are
the app's, not a rule restated here. Per wall: its emitted start -> end, thickness, base and the way
side A faces. Per door: type, swing, size and leaf kind (flush, glazed, panelled); the rooms on side
A and side B (whose floor holds a point 0.3 m beyond each face, within 0.4 m of the wall's base);
the start-side and end-side jambs; the hinge (which jamb, and the pivot: on the centreline for a
flush leaf, 22 mm toward the side it opens to for a leaf hung on the kit's knuckles, such as the
glazed doors); the side, compass point and room it opens into; the leaf at 90° (the plan's drawn
arc) and its tip at Door.js's full opening angle (`0.52 * Math.PI`, 93.6°, read from the hinge
Door.update turns), with how far that tip passes the hinge jamb along the wall (56 mm for a 0.9 m
flush leaf, 34 mm for a hung one): the strip beside the hinge where an open leaf leans over whatever
stands against the wall. Points are site coordinates, then building-local ones `(L x,z)`.

In the app's terms: `_left` hinges on the start-side jamb and `_right` on the end-side one;
`outward` opens to side A and `inward` to side B; kit.js's `wall()` makes side A face its `outside`
point by swapping start and end, which swaps the jambs too. So check each door's hand against the
plan from this output, never from its swing name (a review found eight Ladonia doors hinged on the
wrong jamb that way).

Run `node .../doors-dump.mjs [id-substring ...]`: the positional arguments keep the doors whose wall
or opening id contains any of them. Flags: `--scene <path>` (default `scenes/kosinozici-villas.json`),
`--gen <dir>` (the generator folder, default `scripts/spaces/ladonia`: the building frames, and the
spec under `--live`; a value is taken only when it names a folder, so `--gen c-g-` reads `c-g-` as a
filter), `--live` (the generator's output through `validateScene`, as seeding does), `--export
<name>` (which export of `index.js` is the spec; default the first with `walls` and `furniture`),
`--frame <tag>=x,z[,y]` (repeatable: a building's frame by hand, over the generator's), `--frame
none` (site coordinates only), `--json` (one object per door). It takes well under a second.

Building frames: `_doors.mjs` imports `<gen>/kit.js`, wraps `Building`'s methods, then runs
`<gen>/index.js`, recording each building's `tag` and offset (`ox`, `oz`, `oy`) the first time it lays
anything down; an id belongs to the building whose tag it starts with (`<tag>-`). A project whose
kit is a copy of Ladonia's needs nothing more; otherwise pass `--frame`. The `frames:` line names
them (Ladonia: a [0, 0, 0], b [0, 24.2, 0], c [2.5, -21, -1]); with none, points are site only.
Ladonia-specific: the two defaults (scene and generator paths), nothing else.

## door-swing.mjs: leaves against furniture and against each other

It sweeps every swinging leaf, built and posed as in doors-dump, from shut to Door.js's full
opening angle every `--step` degrees (default 1), against:

- every piece of furniture within the leaf's reach whose height range meets the leaf's, as its
  catalogue box: the catalogue `size` at the placement's scale times the item's, standing on its
  position, turned by its rotation plus the item's `yaw` (the GLBs are centred on that box, so it
  holds the mesh);
- with `--mesh`, the GLB's own triangles (node transforms applied, placed as FurnitureLibrary places
  them) for every piece whose box the leaf touches;
- every other door's leaf standing fully open, within reach and at the same height (two Ladonia
  leaves crossed this way before they were re-hung).

The leaf is Door.js's slab: the opening's width less 1 cm, its height less 2 cm, 40 mm thick (a
glazed frame 48 mm). Handles and glass doors' pull bars, up to about 6 cm proud near the free edge,
are not swept. Pieces lower than SceneBuilder's `FLAT_HEIGHT` (rugs) are skipped unless `--rugs`.

Depth is how far the leaf would have to move to clear the piece: across its thickness either way,
back from its free edge, or up or down, whichever is least. A leaf grazing a WC's rim reads a few
millimetres; one passing into a piece reads its full thickness, printed `through`. Each contact gives
the depth, the angle it starts at (refined to 1/64 of a step), the angle of the deepest contact and
where along the leaf it lies (metres from the hinge), and the depth fully open, where the app parks
an open door. A box contact whose mesh is clear is box-only (an L-shaped sofa's empty corner).

Run `node .../door-swing.mjs [--mesh] [id-substring ...]`: the filters choose the doors swept; all
furniture and all other leaves still count. Flags: those of doors-dump (`--scene`, `--gen`,
`--live`, `--export`, `--frame`, `--json`), and `--mesh`, `--step <deg>`, `--min <m>` (list contacts
deeper than this, default 0.001), `--fail <m>` (default 0.005), `--rugs`, `--all` (every contact,
box-only ones included). Output: per door its swing, hinge and the room it opens into, then each
piece with a `box:` line (and a `mesh:` line), then `Leaf against leaf (the other door fully
open):`, then `SUMMARY: N leaves swept; furniture contacts: … box (… over 5.0 mm), … mesh (… over
5.0 mm; … box-only); leaf against leaf: …`. It exits 1 when a contact (the mesh depth with `--mesh`,
else the box depth) or a leaf against a leaf is deeper than `--fail`, so run it with `--mesh` before
acting on a box contact; it takes under a second, `--mesh` included. Ladonia on 2026-10-04: 71 leaves; 4
box contacts, 2 of them box-only (the glazed `a-g-n-o2` and `b-g-n-o2` pass through the chaise
sofas' empty corner); the C2 and C3 bathroom leaves graze the WC by 3.4 mm, from 93.2° to fully
open; no leaf against a leaf. Ladonia-specific: the defaults only.

## entrance-check.mjs: the street flights through the retaining wall

For each street flight (stairs whose id starts `steps-`) it prints the steps' geometry and the
collision ramp's height, and every element overlapping the flight or its walking corridor. Each
element gets a verdict: BLOCKS (collidable 0.15 to 1.9 m above the walking surface), NARROWS (only
at the edges), BELOW, or VISUAL. It then runs a capsule path search from the parking to the path,
looks for holes in the walking surface past the head, and finds near-coplanar horizontal faces
(under 15 mm apart). Run `node .../entrance-check.mjs [scene.json]`. Flags: `--simulate-fix`
(applies the once-proposed generator fixes in memory: path slabs ending at the head, trimmed terrain
holes, retaining-wall ends buried in the cheeks — they are in `index.js` now, so for Ladonia it
changes nothing; keep it as a pattern), `--width=<m>` (with `--simulate-fix`, sets the flights'
width), `--verbose`. Look for `capsule ...: PASS` or `FAIL` per flight and the last line `all
flights PASS`. It exits 1 on any failure, and when it finds no flight to check. Ladonia-specific:
the `steps-0/1` to A/B name map (C has no street flight now), flights running west, the `*-path`
rooms, the `rw-<n>` retaining-wall ids, the `x > 20` street-side hole filter, and everything under
`--simulate-fix`, which mirrors a specific `index.js` diff.

## zfight-check.mjs: coplanar and near-coplanar surfaces

It rebuilds every surface as the builders lay it down: room floors and ceilings as double-sided
planes, wall panels around openings, thresholds, window frames, glass and blinds, Door.js linings,
roof slabs, stair steps, landscape walls, copings, kerbs, pergolas, planters, railings, pool and
its steps, road paint, terrain, hedge cores, and furniture catalog boxes. It reports overlapping faces closer than
the tolerance, with the polygonOffset layering MaterialLibrary and LandscapeBuilder apply and the
distance at which each gap starts to fight given the camera's near plane. It also reports paint
off its slab, terrain or grass through slabs, slabs or walls over stair treads, and planter/soil
clashes. Run `node .../zfight-check.mjs [scene.json]` (put the scene path first: a positional
argument right after a flag is read as that flag's value). Flags: `--source` (the generator,
validated), `--all` (also list hidden and polygonOffset-resolved cases), `--tol <m>` (default
0.0101), `--json <out.json>` (also write the findings there), the flags that put back the
old layering to compare (`--floors-front`, `--lining-plain`) and the what-if `--outer-pad-lines`.
It models the app's depth layering (MaterialLibrary `layer`, `getTrimFront`, `getTrimBehind`)
and Camera.js's near plane (0.05) by hand: when those change, change `offsetOf` and `NEAR` here
too. The in-page `zfight.js` reads the real offsets and catches same-layer fights this model
misses; only this script reports INVERTED layering (a surface in front layered behind). Look at the `SUMMARY of
visible coincidences by status` table: the FIGHT and INVERTED columns are real flicker, while
`layered`, `same-colour` and `hidden` are not. Then read the `== <category>` sections. Ladonia-specific:
the A/B/C offsets (read from `A_AT`, `B_AT` and `C_AT` in `scripts/spaces/ladonia/index.js`, with
fallbacks) used for building-local coordinates, and the generator path behind `--source`.
Everything else follows the app's builders. A pool's `steps` (2026-10-16) are laid out by
`shared/landscape.js`'s `poolSteps`, which the builder reads too: the treads, their flush stone
nosings and the coping meet without a fight (Ladonia's B pool: 0 stair fights; 23 hidden
same-colour contacts, listed with `--all`). The steps' ramp is unseen and not modelled.

## c-grade.mjs: building C at street level

It checks that C sits at the street's level. Section 1 gives C's vertical offset per element kind
(scene value minus the `c.js`/`furnish.js` local value), which should all be the same, -1.00.
Section 2 covers the street on C's stretch (flights, retaining walls and cheeks, terrain holes,
front hedges). Section 3 covers the ground (terrain over C and next to A, the step and the wall
that hides it, paving floating or buried, lawns and beds crossing the boundary). Then come
coplanar landscape walls, slabs over the street steps, the floor under each spawn and furniture
within the capsule, and `ladonia-views.js` poses 12, 13 and 14 and C's plan cuts against C's level.
Run `node .../c-grade.mjs`. Flags: `--code` (built live from the generator's `index.js`),
`--code=<path>` (another `index.js`; section 1 still compares against the repo's own `c.js` and
`furnish.js`), `--validate` (with `--code`: through `validateScene` first),
`--views=<path>` (default: the skill's `ladonia-views.js`). Look for `✗` lines and the closing
`N problem(s).` (it always exits 0). Ladonia-specific throughout: `STREET -1.0`, `WALL_X 20.2` (the
street-front wall line), `PLOT_Z [-25.5, 44.7]`, `C_AT [2.5,-21]`, the A/C boundary-wall heuristic
(falls back to z = -4.2), the `parking-c` slab, and the pose numbers in `ladonia-views.js`. Treat it
as a pattern for "is this building at grade with its street" rather than something to reuse as is.

## people-plans.mjs: the people planner over many seeds

It plans a space's people (`planPeople` of `shared/people.js`, called as `npm run people:place`
calls it) once for each seed against the seeded scene, the catalogue, `seats.json` and the people
index as built (`public/models/people/index.json`, else the stand-in's), and holds every plan to
the planner's own rules:

- the same plan twice; ids `person-1`… in order; no two on one seat or lounger; no character twice
  until all are used, and none twice in a group;
- standing: on an outdoor floor, `MARGIN` from its edge and from the nearest obstacle (the widest
  margin the site's own `clearOf` passes, by bisection), a group's members `SPACING` apart, no clip
  twice in a group and a drink in every group; any two people `APART` (less `FORWARD_MOST` where
  one of them sits);
- clips: of the pose; none made for the other sex; none of `LEFT_OUT`; a drink only in a hand the
  index says holds (`hand`), and a drinking clip always with the bottle; lying, only a towel,
  sunglasses or an open book, the sunglasses only on a character whose `eyes` the index has;
- seats: on the seat's point (`FORWARD_MOST` forward at most) and facing as it does; feet within
  `FEET_MOST` over and `UNDER_MOST` under the floor (the index's `sits` for that character and
  clip, else the clip scaled by the hips); knees `LEG_CLEAR` and, on a base not open, ankles
  `HEEL_CLEAR` before the front edge; feet short of what stands before the seat; a clip sat back in
  only on a deep soft seat out of doors; a lier on its lounger's point and along it, and no clip
  that sits up of itself on a raised back;
- the order (the first standing group, those lying by a pool, those sitting out of doors, then in,
  the rest) and who the first 4 and the first 8 drawn are (a phone's `people.most`);
- the validator: `sanitizePeople` and `validateScene` keep the plan as it is, and the same a second
  time.

Then it sweeps counts of 0 to 40, the stand-in index and no index at all, three characters' eyes
taken out of the index (none of them may get sunglasses), and `planOne`, the editor's Add, near
people of each pose of seed 3's plan. Last it reads the scene's saved `people` by the same rules,
as notes only: a vetted plan carries hand edits, and the editor may put anyone anywhere.

Run `node .../people-plans.mjs <scene-id>` (the id is required). Flags: `--seeds <n>` (seeds 1 to n,
default 20), `--seed <n>` (that seed alone, its plan listed, the sweeps and the saved plan skipped).
Read the statistics for what a pass still lets through: `standing: nearest obstacle … m`, `sitting:
feet … cm off the floor`, `the first 4 drawn`, and the `clips:` and `seats:` counts (a clip or a kind
of seat never used means a rule too tight or a measurement off). Then look for `No problems.` or
`N PROBLEMS:`, one line a seed and person. It exits 1 on any problem and 2 when it could not run (no
such scene, no `seats.json`, a constant gone), and takes 2.4 s for Ladonia. The limits are read from
the `const` lines of `shared/people.js` itself (the `rules` line prints them), so a change there is
followed, and a constant renamed or removed stops the run with its name. Run it after any change to
`shared/people.js`, to `seats.json` (`npm run seats`), to the index (`npm run people`) or to a
space's furniture, before placing people.

It says nothing of how a plan looks, a clip's arm through a chair's rail or a head off a headrest:
that is `people-audit.js` (the skill's folder: in the page, by skin). Ladonia on 2026-10-10: 20
seeds of 12 people (98 standing, 71 sitting, 71 lying), no problems; nearest obstacle 0.40 m,
sitters' feet 0.2 cm off the floor on average and 1.5 at worst; the saved 12 are off none of the
rules. Against a copy of the planner with three rules taken out (the bottle, `LEFT_OUT`, the
standing margin) it listed all three kinds and exited 1. Ladonia-specific: nothing; the scene is the
argument, and the catalogue, `seats.json` and the index are the repo's.

## Small helpers

- `_glbbox.mjs`: for every catalog item used by a `c-` piece in the seeded scene, the catalog
  `size` and `yaw` against the GLB's real min/max. Use it to catch catalog sizes that don't match
  the mesh. The scene file and the `c-` prefix are Ladonia-specific.
- `_glbparts.mjs <catalog-id>...`: a bounding box for each primitive (node, material) of a GLB.
- `_modes.mjs <catalog-id>...`: triangle count without the opening parts, the opening parts, and
  the collision mode the game will use (since 2026-10-16: the catalogue's `collision` if set; else
  box when the piece without its parts has more triangles than `SceneBuilder.MESH_COLLISION_BUDGET`,
  else mesh, "+ N shut boxes" for its parts; a "shower door" is a way in with no box).
- `_plan.mjs [generator-dir]`: building C's walls (with openings), rooms, stairs and floor openings
  as `c.js` lays them out in C's own frame. The default is the repo's `scripts/spaces/ladonia`.
- `_hands.mjs <glb | catalog-id>...`: each opening part of a GLB, its label, its box shut in the
  piece's frame, the edge it hangs on and its swing (or its slide), by height and along x, so a
  run's hands read left to right as the piece faces north at rotation 0.
- `_doors.mjs`: not standalone — the door tools' shared module (arguments, loading the scene or the
  generator, building frames, rooms, and the doors built and posed with `Door.js`). The other
  helpers above are standalone; nothing imports them.

## part-sweep.py: every opening part of a scene against what stands round it

It sweeps each placed piece's opening parts (the GLB nodes with `extras.opens`, their real surface
sampled every 2 cm) from shut to open in `--steps` poses against every other placement's catalogue
box as placed and every wall (solid, openings included), and gives for each part that runs into
something how deep (mm), at what share of its swing, into what, and how far into it the part already
was shut — a placement's own overlap. It is the scene-wide counterpart of `models/sweep.py` (each
piece against its own parts, before export), and does offline what the app does at run time
(`Openable.plan` stops a part at what is in its way): on Ladonia its hits were exactly the app's 32
stops (22 kitchen clashes + 10). A placement builder who does not run the app sweeps with it. It
needs numpy, which this Mac's python3 lacks: run it with Blender's own python,
`/Applications/Blender.app/Contents/Resources/5.1/python/bin/python3.13 <skill>/checks/part-sweep.py
<scene.json> [<glb-dir>] [<fallback-glb-dir>] [--steps 18] [--tol 0.005] [--only prefix,...]`.
`<glb-dir>` is looked in first (a Blender copy's `glb/`, `models/export_scratch.py`'s out), then the
fallback (default the repo's `public/models/furniture`, whose `catalog.json` gives the sizes);
`--only` keeps the pieces whose catalogue id starts with one of the prefixes. Output: `CLASH
<placement> <catalogue id> <part> <label> <mm> mm at t <share> (shut <mm>) into <what>`, then
`PARTS <n> CLASHES <n>`. Ladonia, all parts: 5 min 15 s; `--only ld-kitchen` (144 parts) on
2026-10-17: 16 clashes. Ladonia-specific: nothing; the scene is the argument. Parts'
nodes are taken unrotated, as `join_piece` writes them.

## Every tool in this skill's folder

The node checkers above are this folder's. The rest of the skill's tools are one folder up, and
`models/` (its own `README.md`). In-page tools run in a page of a TEST server (never the user's on
:3000), loaded through the sink:
`await eval(await (await fetch("http://127.0.0.1:3199/<file>?" + Date.now())).text())`. `sink.py`
and `serve.py` serve the skill folder's top-level files by name (JSON too), so a page can load any of
them from either, but nothing in `checks/` or `models/`. Each file's header says what to load before
it, what each call does and what it returns. The order in a test tab: `boot.js` right after the
navigation, then `act.js`, then the feature's own tools. Start both servers once a session, in the
background, writing into the scratch folder:

    python3 <skill>/sink.py <scratch>/frames            # 127.0.0.1:3199
    python3 <skill>/serve.py <scratch>/frames 3187      # the tools server and the baton

A restart of the machine empties the scratch folder: a tool worth keeping goes into this folder, with
a header in the style of these, the same session it is written.
